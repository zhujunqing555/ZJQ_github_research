# 报告、去重和状态

## 每日卡片

报告按用户本地日期保存。首轮最多3个重点，允许科研多于其他赛道，不要求每日每赛道一条。质量通过但热度未知的首月成熟项目可以推荐，标签如实。

```
名称｜赛道｜原生skill / MCP / 包 / CLI / 教程｜质量分
原始仓库、具体入口和示例链接
本周热度 / 成熟首次发现 / 必要配套；发布日期与统计日期
热度：总Stars、近7天指标、时间口径、数据完整性（未知就写未知）
任务与增量：相比本地已有能力具体新增什么
输入 → 本项目输出 → 后续工作流
使用条件：Windows/WSL、语言、账号/GPU/模型/费用和待配置项
核验：文档/源码已读 / 官方案例核验 / 已试跑（实际运行后才能写）
最小试用：示例输入、入口、预期结果、成功判断
建议：可选安装 / 先配置 / 值得封装 / 暂观察
```

额外论文链接用于支撑科研证据，不能替代仓库链接。不要把预测写成已验证机制、把制作工具写成自动文生视频、把草稿写入写成群发成功。文献改写工具还须保留事实/数字/引文，图表处理不得改变科研数据内容。

## 状态文件

- `config.json`：界面名/调用标识、首次启用日期、时区、由启用日期计算的首月边界、可调整的检索比例、建议节奏、主推上限和已成功创建的自动化ID。初始化只创建缺失文件，安装或迁移不等于启用定时任务。
- `tasks.json`：任务id、赛道、关键词族、输入输出、当前痛点。
- `sources.json`：可信种子仓库/组织、用途、核验日期；非自动推荐白名单。
- `candidates.json`：每项 id=`owner/repo::entry`、repo_id、canonical_repo、entry、track、kind、first_seen、quality_score、quality_reason、sources、verified_at、verification_level、heat_status、requirements、last_delivered、last_commit或指纹、delivery_reason；只保存有证据的字段。
- `feedback.json`：用户反馈的原话或准确摘要、时间、candidate_id、标签；无回复不添负面标签。
- `runs/`：原始元数据、热度证据、快照和覆盖错误，供复查。
- `reports/`：已生成报告。记录 report.status=`prepared/delivered`；只有展示给用户后才标delivered，不把先前设计举例当成已完成日报。

状态目录默认解析为 `CODEX_HOME/skill-radars/zjq-github-research`；未设置 `CODEX_HOME` 时以用户主目录下的 `.codex` 代替。自定义路径以用户指定或初始化的 `--state-dir` 为准。`templates/` 是首次运行的公开默认模板，不保存个人画像、候选使用历史、采集快照或账户信息。

保持各文件JSON有效，使用同目录临时文件+replace或等效原子写入，修改前读现有版本，保护并发/用户改动。历史数据不因当日失败覆盖为空。反馈与安装状态不随采集刷新被覆盖。

## 周榜与反馈

周日以本次候选库内的已核验热度为依据形成周榜，重述项目须标本周汇总，不能当新增重复推送。列本周新增有效能力、已试用结果和覆盖缺口。检索失败或没有有效发现如实分别记录。

安装指令需指向具体候选；可从当前聊天解析“安装第2个/安装Remotion”。明确选择就继续对应安装流程，不再泛问许可；与未指定项目、第三方收费、账户接入、正式发布无关的权限仍不由雷达授予。
